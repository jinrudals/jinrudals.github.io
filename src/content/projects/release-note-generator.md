Semifive에서 SoC 프로젝트를 할 때 만든 릴리스 노트 자동화 도구입니다. 태그 사이의 커밋만 정리하는 데서 그치지 않고, 실제 파일도 계층 구조를 따라 비교해 릴리스에서 무엇이 바뀌었는지 정리했습니다.

## 왜 만들었나

제 왼편에 Project Leader가 있었는데, 릴리스할 때마다 변경 사항을 파악하고 문서로 정리하느라 고생했습니다. 프로젝트 전체의 세부 변경을 한 사람이 매번 다 알고 있기는 어렵고, 커밋과 이슈를 일일이 확인해 Confluence에 옮기는 일도 반복됐습니다.

그래서 릴리스 때마다 필요한 정보를 모아 보고서로 만들고, Confluence에 남기는 과정을 자동화했습니다.

## 무엇을 비교했나

태그가 만들어지면 이전 태그 이후의 커밋을 확인했습니다. 하지만 커밋 목록만으로는 실제 파일이 어떻게 달라졌는지, 그 변화가 SoC 설계 흐름에 어떤 의미인지 알기 어려웠습니다. 그래서 파일도 비교하고, 계층 구조를 따라 변경 위치를 정리했습니다.

예를 들어 Memory 관련 변경은 합성을 다시 해야 하는지, 그리고 HPDF(Hierarchical Physical Design Flow)의 각 단계에서 재합성이 필요한지를 확인할 수 있도록 보고서에 담았습니다. 비교 자체는 단순한 diff였지만, 변경된 파일을 hierarchy에 맞춰 보여주는 것이 중요했습니다.

## 어떻게 사용했나

Python으로 GitLab, Jira, Confluence API를 연동했습니다. 태그 간 커밋과 실제 파일 변경을 모으고, Jira 정보를 함께 확인해 변경 내용을 정리한 다음 Confluence 문서로 생성했습니다.

릴리스 노트에는 단순히 변경 목록만 적는 게 아니라, Project Leader가 변경 범위와 합성 필요 여부를 파악하는 데 필요한 내용을 담았습니다.

## 기술 스택

- **Python**: 데이터 수집과 보고서 생성
- **GitLab API**: 태그와 커밋 정보
- **Jira API**: 프로젝트 이슈 정보
- **Confluence API**: 릴리스 보고서 작성
- **파일 비교**: 변경된 파일을 hierarchy에 따라 정리

## 돌아보면

### 필요한 데이터는 쓰는 사람이 안다

API에서 가져올 수 있는 데이터와 실제 업무에 필요한 데이터는 달랐습니다. 만드는 입장에서는 커밋과 이슈를 모으면 될 것 같지만, Project Leader에게는 "그래서 합성을 다시 해야 하나?"에 답할 수 있는 정보가 필요했습니다.

무엇을 수집할지 정하기 전에, 이 문서를 보는 사람이 어떤 일을 하고 무엇을 판단해야 하는지부터 알아야 했습니다. 필요한 데이터는 제가 정하는 게 아니라 실제로 쓰는 사람의 요구사항에서 나오는 것이었습니다.

### 변경 목록보다 그다음 할 일

이 도구를 만들면서 릴리스 노트는 커밋 메시지를 모아 놓는 문서가 아니라는 걸 배웠습니다. Project Leader에게 필요한 건 무엇이 바뀌었는지뿐 아니라, 그 변경이 실제 작업에 어떤 영향을 주는지였습니다.

커밋과 파일을 함께 보고, Memory 변경에 따른 합성 여부와 HPDF 단계별 영향을 보고서에 담은 것도 그 때문입니다. 반복해서 정보를 모으는 일은 자동화하고, 사람이 판단해야 하는 부분은 판단할 수 있도록 필요한 맥락을 제공하는 데 초점을 뒀습니다.
